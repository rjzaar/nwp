## 1. What F26 is, and the nwc↔ss decision

F26 as written makes **AVC** the OIDC issuer and **SS** (Moodle) the client, to
give AVC↔SS single sign-on. P72 needs the identity to resolve into **nwc**
(the canonical 2.0 site that owns the editorial pipeline and guild membership),
which F26 lists as an explicit **non-goal** ("adding another site … would require
a separate proposal").

**Decision taken (logged §6): P72 §3.2 _shape 1_ — nwc becomes the issuer for ss.**
Rationale: the identity that must land on the nwc editorial "propose" form is an
**nwc member**, so making nwc the issuer means the `sub` in the ID token *is* the
nwc uid with no second reconciliation hop. This also matches the substantial
**pre-existing** nwc-side code (already nwc-branded, see §2). Shape 2 (nwc as a
second relying party behind an AVC issuer) was rejected as more moving parts for
no benefit to P72. **This choice is exactly the auth-graph edge that needs your
sign-off.**

## 4. Security model (no shortcuts)

- **Flow:** standard OIDC **authorization-code + PKCE (S256)**. The `ss_moodle`
  client is **confidential** with a **per-client secret generated at provision
  time** (not a shared static token), stored hashed by simple_oauth and written
  locally to a **gitignored** file — never committed. There is **no shared-secret
  hand-off, no bearer token in a deep-link, and no anonymous auto-create** (the
  exact shortcuts P72 §3.3 / §5 forbid).
- **UID-lock:** `mdl_user.idnumber` == nwc uid (`sub`). After first lock, the user
  is resolved by `idnumber`, **never by email**; email/name are refreshed but the
  lock never changes (F26 §3.2). Verified in unit tests ("idnumber beats email").
- **`sub` is trusted, not user input:** it is the subject of an ID token signed by
  the nwc issuer (RS256) and verified by Moodle core OAuth2 against nwc's JWKS.
  An empty/unsigned `sub` → **deny** (never create/guess).
- **Legacy email link is one-time and gated:** binding a pre-OIDC Moodle account
  by email happens only when `link_legacy_by_email` is ON *and* the ID token says
  `email_verified === true`. Because the email is asserted by the trusted issuer
  (not typed by the client), this is not an account-takeover vector. Turn the flag
  OFF outside a migration window.
- **Signing keys are per-site, never from prod:** the `oauth-keys/` on nwc-dev
  were generated locally. F26 §4.1 makes "never copy the prod signing key into a
  preview/dev" load-bearing; this build honours it and the provision script never
  copies keys from anywhere.
- **Deterministic sanitizer email-hash** (F26 §3.3) is already in tree
  (`lib/sanitizers/oidc-email.sh`): `sha256(email‖salt)[:16]@sanitized.test`, salt
  in `.secrets.data.yml` (AI cannot read it), never rotated (F26 §4.2). Salt never
  logged; empty input → empty output. 15 bats tests pass.

   intentionally absent — adding them is F26 Phase 6 (2-approver, human, never CI).

   and has no UID-lock. `auth_nwc` supersedes it for nwc↔ss; decide migration.

   Moodle OAuth2 service config.
